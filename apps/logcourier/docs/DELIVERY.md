# Доставка с учётом лимитов Telegram

## Наблюдение 2026-09-06

При чтении закреплённого каталога указанной пользователем закрытой группы найдены
32 записи: каждый ZIP размером 713–1760 байт. Старый код отправлял до 32 документов
за проход, без интервала между ними, затем добавлял каталог и закрепление.
В журнале пользователя — HTTP 429 с `retry_after=37`. Пауза соблюдалась до
следующей попытки, но сохранение настроек обнуляло её в памяти.
Сообщения группы не удалялись, реальные файлы логов не скачивались; читался каталог.

## Решение

1. Локальный сбор сохраняет небольшие фрагменты и позиции чтения транзакционно.
   Частота сбора не определяет количество сообщений в Telegram.
2. Только когда наступил срок отправки, ещё не отправленные фрагменты объединяются
   в пакеты. Предел — 19 000 000 байт после упаковки или 4096 фрагментов. Пакет
   состоит из неизменённых исходных ZIP и манифеста с метаданными и SHA-256.
   Исходные строки очереди заменяются пакетом в одной транзакции; при сбое откат.
   Уже получившие `file_id` строки не перепаковываются.
3. Неполный пакет уходит по интервалу или явной ручной команде. Не ждём бесконечно,
   пока наберутся мегабайты. Большая очередь разбивается на несколько пакетов;
   не более четырёх пакетов за цикл, чтобы возвращаться к сбору и обработке настроек.
4. Между документами и закреплениями одной группы минимум 4 секунды; для бота
   дополнительно минимум 1 секунда. Слоты записываются на диск **перед** запросом,
   поэтому повторный запуск не позволяет повторить мгновенную серию сообщений.
   При ожидании проверяется отмена; UI не блокируется.
5. Каталог включает пакеты, а не каждую внутреннюю ZIP-запись. После подтверждения
   загрузки сохраняется `file_id`; сбой закрепления не вызывает повторную загрузку.
6. Полученный 429 сохраняет время запрета для всего бота: `retry_after` плюс секунда
   запаса. Если Telegram не дал время, ждём 60 секунд плюс запас. Значение не
   обрезается до часа. Все запросы фоновой доставки ждут завершения этого запрета;
   он не сбрасывается кнопкой отправки, сохранением настроек или перезапуском.
7. При полной очереди и нехватке места на обёртку пакета разрешена доставка старых
   фрагментов по тому же ограничителю частоты — освобождение очереди не блокируется.

## Почему не 50 МБ и не ровно 20 сообщений/мин

[Bot API FAQ](https://core.telegram.org/bots/faq) указывает: загрузка до 50 МБ,
скачивание через `getFile` до 20 МБ; максимум 20 сообщений/мин в группе,
рекомендуется не чаще одного сообщения/сек в одном чате. Чтобы эти логи можно было
потом скачать ботом, используем максимум 19 МБ. 4 секунды между операциями дают
запас под каталог, служебные сообщения и пограничные моменты скользящего окна.
Это не искусственное заполнение файла до предела и не платные рассылки.

Нельзя гарантировать полное отсутствие 429: тот же токен может использовать другая
копия программы, а ограничения сервера могут меняться. Ограничитель предотвращает
известные локальные всплески, а серверный 429 переводит доставку в ожидание без
потери очереди. Он не служит разрешением обходить ограничения Telegram.

## Совместимость и проверка

- Старая SQLite-очередь читается без миграции схемы. Компактируются только строки
  без подтверждённой доставки; старые опубликованные файлы и каталоги не меняются.
- CLI скачивает новые пакеты как ZIP, старые архивы остаются доступны. При анализе
  нового формата нужно прочитать манифест и внутренние ZIP.
- Тесты проверяют объединение 32 файлов, побайтовую сохранность, размер пакета,
  откат при нехватке места, сохранение подтверждений, лимит для закрепления,
  перенос `retry_after` между клиентами и прерывание ожидания.
- Реальные запросы в пользовательскую группу не использовались для искусственного
  вызова 429. Проверка нового ограничителя — на имитированном API и управляемом времени.

## Разделение версий KeySwitch (текущая доработка)

Поверх существующей очереди добавлены устойчивые маркеры версии и поле
`keyswitch_version` у каждого нового фрагмента. Маркер — небольшой JSON-документ
с подписью в группе, учитываемый тем же ограничителем частоты, что и архивы.
Фрагменты с разными версиями/источниками KeySwitch не объединяются в один пакет.

Закреплённый каталог содержит `keyswitch_versions`: текущую подтверждённую
версию каждого активного источника, предыдущую версию, ID маркера и время
определения. Эти дополнительные поля совместимы со схемой каталога 1;
старые читатели их игнорируют, поэтому **для автоматического отбора по версии
нужен обновлённый CLI**. Старые каталоги читаются через `--all-versions`.

Позиция файла и версия текущего фрагмента записываются одной транзакцией.
Маркер и указатель текущей версии также фиксируются вместе: переполнение
очереди не приводит к потере ещё не поставленного в очередь маркера.
Версия актуального файла проверяется независимо от объёма исторической очереди.
Порядок прихода сообщений в Telegram не определяет версию архивов.

`list`/`fetch` по умолчанию фильтруют по текущей версии; лимит применяется
после этого фильтра. Маркеры и архивы с неизвестной версией не выдаются как
актуальные данные. В CLI создаётся изолированная завершённая подборка с
`selection.json`; старые файлы в родительском каталоге не входят в неё.
