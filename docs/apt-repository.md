# Репозиторий APT: публикация и ключ подписи

Установленный KeySwitch обновляется штатными средствами Ubuntu. Пакет приносит
с собой источник APT и открытый ключ, а выпуск публикует подписанный репозиторий
на GitHub Pages. Здесь описано, из чего это собрано, что нужно включить один раз
и что делать при смене ключа.

## Что где лежит

| Файл | Роль |
| --- | --- |
| `packaging/debian/keyswitch.sources` | Единственное место, где записаны адрес, suite, компонент, архитектура и путь к ключу. Ставится как conffile в `/etc/apt/sources.list.d/keyswitch.sources` |
| `packaging/keyswitch-archive-keyring.asc` | Открытый ключ репозитория; ставится conffile'ом по пути из поля `Signed-By` (`/etc/apt/keyrings/`) |
| `packaging/apt-index.html` | Шаблон страницы, которую видит человек, открывший адрес репозитория |
| `tools/apt_repository.py` | `build` — сборка и подпись репозитория, `verify` — проверка готового дерева |
| `tools/make-apt-signing-key.sh` | Создание ключа подписи и подсказка, какие секреты завести |
| `.github/workflows/release.yml`, задание `apt-repository` | Публикация репозитория на Pages до создания выпуска |

Источник и ключ поставляются как conffiles, поэтому решение пользователя
переживает обновления пакета, а `apt purge` убирает оба файла. Ключ лежит
именно в `/etc/apt/keyrings`, а не в `/usr/share/keyrings`: файл из `/usr/share`
пропал бы при `apt remove` вместе с приложением, источник при этом остался бы,
и каждый `sudo apt update` заканчивался бы ошибкой `NO_PUBKEY` (проверено:
`apt-get update` с отсутствующим файлом `Signed-By` завершается кодом 100).

Lintian запрещает пакетам класть файлы в `/etc/apt/sources.list.d` тегом
`package-installs-apt-sources` — правило архива Debian, куда KeySwitch не
входит. Тег снят именованным override в `packaging/debian/lintian-overrides`
с объяснением; остальные проверки lintian остаются строгими.

Адрес репозитория не повторяется ни в сборщике, ни в проверке: обе стороны
читают его из `packaging/debian/keyswitch.sources`. Задание выпуска дополнительно
сверяет адрес, который выдаёт GitHub Pages, с адресом из этого файла и падает при
расхождении — иначе пакет доверял бы одному адресу, а обновления лежали бы по
другому.

## Что публикуется

```
/                             index.html, keyswitch-archive-keyring.asc
/dists/stable/                Release, Release.gpg, InRelease
/dists/stable/main/binary-amd64/  Packages, Packages.gz
/pool/main/k/keyswitch/       keyswitch_<версия>_amd64.deb
```

В пул попадает текущий пакет и пакеты не более чем из пяти последних выпусков
(`POOL_RELEASES` в задании): один `.deb` занимает около 17 МБ, а у GitHub Pages
сайт ограничен 1 ГБ, мягкий предел трафика — 100 ГБ в месяц, и Pages не
предназначен для коммерческого хостинга
([ограничения GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).

## Что нужно включить один раз

1. В настройках репозитория: **Settings → Pages → Build and deployment →
   Source: GitHub Actions**. Токен рабочего процесса не может включить Pages сам.
2. Два секрета репозитория:

   ```bash
   ./tools/make-apt-signing-key.sh .t/apt-signing
   gh secret set KEYSWITCH_APT_SIGNING_KEY < .t/apt-signing/private-key.asc
   gh secret set KEYSWITCH_APT_SIGNING_PASSPHRASE < .t/apt-signing/passphrase.txt
   cp .t/apt-signing/public-key.asc packaging/keyswitch-archive-keyring.asc
   ```

   Закрытая половина ключа и пароль не должны попадать в Git: каталог
   `.t/` игнорируется, а в пакет уходит только `public-key.asc`. Сборка пакета
   отказывается класть в него файл, в котором есть блок закрытого ключа.

Действующий ключ: RSA-4096, отпечаток
`39C7 0828 2A8E 4E3E 65C4 FAAB DA3D 9DDE F3E4 DE64`, создан 22.09.2026,
годен до 19.09.2036.

## Порядок выпуска

Задание `apt-repository` зависит от сборок всех трёх платформ и выполняется до
задания `release`: репозиторий не должен получить версию, которую выпуск не
получил из-за красной сборки Windows или macOS. Это намеренно: пакет, который получает пользователь, уже содержит
источник APT, поэтому репозиторий должен быть доступен раньше, чем появится
ссылка на выпуск. Если публикация репозитория не удалась, выпуск не создаётся.

Задание делает по шагам: забирает собранный `.deb`, докачивает пакеты предыдущих
выпусков, сверяет адрес Pages с источником в пакете, импортирует ключ из
секретов, собирает и подписывает дерево, проверяет его и только затем
публикует.

## Проверка без выпуска

```bash
GNUPGHOME=.t/apt-signing/gnupg python3 tools/apt_repository.py build .t/apt-repo \
  dist/keyswitch_<версия>_amd64.deb --passphrase-file .t/apt-signing/passphrase.txt
python3 tools/apt_repository.py verify .t/apt-repo --expect-version <версия>
```

`verify` проверяет подписи через `gpgv` **только** открытым ключом из пакета,
сверяет все контрольные суммы из `Release` и затем заставляет сам APT прочитать
репозиторий по `file://` — тем же кодом, которым его читает установленная
система. Состав пакета (conffile, источник, ключ) проверяет
`tools/verify-native-deb.sh`, модульные проверки сборщика — `tests/test_apt_repository.py`.

## Смена ключа

Ключ, которым подписан репозиторий, обязан оставаться известным уже установленным
пакетам: у них на диске лежит старый `keyswitch-archive-keyring.asc`, и APT
доверяет только ему. Поэтому ключ меняют в два выпуска:

1. В первом выпуске в `packaging/keyswitch-archive-keyring.asc` кладут **оба**
   открытых ключа подряд (`cat старый.asc новый.asc > ...`), а подпись продолжают
   делать старым ключом. Проверено: APT принимает файл `Signed-By` с двумя
   ключами и репозиторий, подписанный любым из них.
2. Когда пользователи обновились, секрет `KEYSWITCH_APT_SIGNING_KEY` заменяют
   новым ключом, а из файла ключей убирают старый.

Подписать один `Release` сразу двумя ключами одним вызовом `gpg` можно только
если у обоих ключей общий пароль: `--passphrase-file` в рабочем процессе один.
Путь из двух выпусков этого ограничения не имеет.

Если ключ скомпрометирован, порядок тот же, но без ожидания: новый ключ вводится
немедленно, а пользователям, у которых остался только старый, придётся поставить
ключ вручную командой из [README](../README.md#обновления-через-apt) или скачать
`.deb` со страницы выпуска.

## Что ломается и как это выглядит

- **Pages не включён или задание не выполнено** — `sudo apt update` у пользователя
  сообщает о недоступном источнике; установленная версия продолжает работать.
- **Срок ключа истёк** — APT отказывается принимать репозиторий с сообщением о
  просроченной подписи. Лечится продлением срока ключа (`gpg --quick-set-expire`)
  и выпуском с обновлённым открытым ключом.
- **Репозиторий переименован или сменился владелец** — адрес Pages перестаёт
  совпадать с источником в пакете, задание падает на шаге сверки адреса до
  публикации.
