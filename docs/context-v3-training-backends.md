# Обучение context-v3 на CPU или GPU

[`tools/train_context_action_model.py`](../tools/train_context_action_model.py) строит
кандидата context-v3 на одном из двух бэкендов. Выбор не меняет результат: любой бэкенд
даёт тот же `context-action.json`, ту же печать `candidate-seal.json` и тот же
`recipe.json`, байт в байт. Бэкенд выбирают по тому, что есть на машине.

```bash
PYTHONPATH=src:tools python3 tools/train_context_action_model.py \
  --corpus <fit> --output <каталог> [--backend auto|cpu|gpu] [--jobs N]
```

| бэкенд | что делает | что нужно |
| --- | --- | --- |
| `cpu` | учебные планы и признаки каждого кадра считает Python тренера в `--jobs` процессах; с `--jobs 1` — в одном процессе, задача за задачей | Linux, компилятор C, NumPy |
| `gpu` | учебные планы — на CPU, как выше; улики и признаки кадров — ядра CUDA; кадры, которые ядра не берут, — тот же Python | то же и CuPy, NVRTC, драйвер NVIDIA для CUDA 13 |
| `auto` (по умолчанию) | `gpu`, если он может работать на этой машине, иначе `cpu`; причину отказа от `gpu` печатает | |

`--jobs` по умолчанию — по процессу на ядро, но не больше, чем позволяет доступная память
(`CONTEXT_ACTION_MAIN_PROCESS_BYTES` и `CONTEXT_ACTION_WORKER_BYTES` в
[`constants/training.py`](../src/keyswitch/constants/training.py)).

Файлы `features-*.jsonl.gz` тренер больше не пишет: их читал только он сам, чтобы
собрать матрицы.

## Установка

```bash
tools/install-training-accelerators.sh          # NumPy: бэкенд cpu
tools/install-training-accelerators.sh --cuda   # и CuPy с библиотеками CUDA: бэкенд gpu
```

Скрипт ставит закреплённые версии в `build/training-site` (каталог игнорируется git);
тренер ищет пакеты сначала там. В облачной сессии Claude Code NumPy ставит хук
[`session-start.sh`](../.claude/hooks/session-start.sh); видеокарты там нет, `auto`
выбирает `cpu`.

## Почему результат один и тот же

- Кадры, учебные планы и их отчёты строят те же функции тренера и складывают в том же
  порядке, что и прежнее последовательное обучение; процессы-работники только делят работу.
- Масса признаков суммируется по Кэхэну в C в порядке кадров, как `FeatureMass`;
  матрицы собираются из тех же записей в том же порядке, что `Packed.build`; маски
  поддержки, выбор эпохи и калибровку считают прежние функции.
- Ядра CUDA повторяют Python операция за операцией: логарифмы берутся только от целых
  и приходят таблицами, посчитанными Python; суммы повторяют `sum` и `math.fsum`
  CPython; сигмоиду intent-модели считает функция Python; свойства символов выгружены
  из методов `str`; сборка без слияния умножения и сложения (`--fmad=false`). Hunspell
  отвечает на CPU; ответы хранятся в `build/context-action-cuda/` по хешу словарей.
- Во время обучения на GPU каждый 64-й кадр (`CONTEXT_ACTION_CUDA_SPOT_CHECK_STRIDE`)
  пересчитывается на CPU; если признаки разошлись, обучение останавливается и называет кадр.

Проверено 06.10.2026 на корпусе v16 (6 ядер, 31 ГиБ, GTX 1660 Ti 6 ГиБ). Во всех режимах
получилась модель `context-v3-0f23c49808ae` прежнего последовательного тренера выпуска 0.39.0;
печать совпала с его печатью во всём, кроме списка закреплённых файлов (в него вошли файлы
бэкендов), а печати бэкендов на одном дереве совпали между собой байт в байт.

| режим | время обучения | пик памяти |
| --- | --- | --- |
| последовательный тренер 0.39.0 | 31 мин | 2,9 ГБ |
| `--backend cpu --jobs 1` | 14,5 мин | 6,4 ГБ |
| `--backend cpu --jobs 4` | 6 мин | 9 ГиБ на все процессы |
| `--backend gpu` | 3 мин | 6,5 ГБ процесс и около 3,5 ГиБ видеопамяти |

На GPU переносятся улики и признаки кадров: на этом этапе GPU в 3–4 раза быстрее всех ядер
CPU. Загрузка корпуса, учебные планы и эпохи оптимизатора (около 80 с в одном потоке) идут
на CPU в обоих режимах, поэтому всё обучение на GPU быстрее примерно вдвое. Облачная сессия
Claude Code (4 vCPU, 16 ГБ, без GPU) обучает на `cpu` в четырёх процессах.

## Сопровождение GPU-пути

Ядра в [`tools/context_action_kernels/`](../tools/context_action_kernels/) повторяют Python:
файлы из `CONTEXT_ACTION_CUDA_MIRRORED_SOURCES` и функции тренера из
`CONTEXT_ACTION_CUDA_MIRRORED_TRAINER_PARTS`. Над функциями ядер написано, какую функцию
Python они повторяют. [`parity.json`](../tools/context_action_kernels/parity.json)
хранит хеши этих исходников на момент последней сверки. Если хотя бы один изменился,
`--backend gpu` отказывается работать, а `auto` выбирает `cpu`: обучение идёт дальше,
только медленнее.

Чтобы вернуть GPU после такой правки, на машине с CUDA:

```bash
PYTHONPATH=src:tools python3 tools/context_action_cuda.py --corpus <fit> --refresh-parity
```

Команда строит кадры всех видов из TRAIN и DEVELOPMENT корпуса (test не читается),
считает их признаки на GPU и в Python для обоих профилей и сравнивает. Если расхождений
нет, она записывает новые хеши в `parity.json`; если есть, печатает первые из них, и
ядро нужно поправить вслед за Python. Без `--refresh-parity` команда только сравнивает.
В облачной сессии без видеокарты это сделать нельзя: там обучают на `cpu`, а сверку
проводят потом на машине с GPU.

Тесты: [`test_context_action_pipeline.py`](../tests/test_context_action_pipeline.py)
проверяет бэкенд `cpu` на Linux (один и несколько процессов против последовательного
расчёта, сборку матриц, массу признаков); [`test_context_action_cuda.py`](../tests/test_context_action_cuda.py)
сравнивает признаки GPU и Python и работает только там, где есть CuPy и видеокарта.
