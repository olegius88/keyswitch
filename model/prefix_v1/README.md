# Prefix v1: обученное переключение на полуслове

С 02.10.2026 установлен `prefix-v2-bf3dc28f8567` (schema 2, [recipe](../prefix_v2/recipe.json),
[seal](../prefix_v2/candidate-seal.json)), принятый только в паре с `context-v3-7d8e1c9b2d87` по
протоколу последовательностей [context v3](../context_v3/README.md): пара воспроизводилась
против замороженных context-v1 + prefix-v1 ([baseline](../prefix_v2/baseline-prefix-v1.json))
в обоих режимах настроек и прошла запечатанный test v16 без порчи правильного текста. Ниже
описан prefix-v1 — базовая линия этой пары.

Отдельный локальный классификатор для незавершённых EN/RU-префиксов.
Рабочий артефакт prefix-v1 — `prefix-v1-1f1d497757cc`, 203 577 байт, 2 653 разреженных
признака, SHA-256 `d6396beecbeee08a6d9165f1aea0b9316a3a75b5f986e464b99a5a1ba738ac7a`.
Это третье поколение prefix-v1: та же схема признаков и те же параметры
обучения, признаки посчитаны по словарям, которые использует движок, новое
разбиение, новое обучение и новый запечатанный test (см. «Предыдущие
поколения»). Модель не использует веса или extractor завершённых слов
context-v1. Решения — оставить, преобразовать или ждать; общий
четырёхклассовый контейнер содержит также `suggest`, но такой метки в этом
обучении нет.

В `assist` при включённых контексте и ранней смене модель оценивает каждый
новый префикс в проверенной области 4–12 символов. При score `convert` ниже
0.985 ждёт продолжения. Это порог, выбранный по calibration, а не обещание
98.5% правильного понимания намерений реального пользователя. Настройка
минимума может задержать проверку; меньший минимум не расширяет область модели.
В `off`/`shadow` и без учёта контекста сохраняется прежний префиксный алгоритм.

## Данные и разделение

Использован уже замороженный публичный
[CC0-снимок Tatoeba](../context_v2/sources/README.md) с его исходной контрольной
суммой. Частные логи и переписка не используются. Из слов строятся авторские
ситуации: верная/неверная раскладка, пустой контекст, комментарии, команды,
идентификаторы, английские вставки и опечатки с удалённой буквой. Каждый
последующий символ образует отдельное наблюдение.

Разделение выполняется **до разворачивания последовательностей** по первым
трём физическим клавишам: варианты языка, контекста и словарного профиля
одного семейства не расходятся по разделам. Общие короткие префиксы из одного
или двух символов имеют метку ожидания и не могут запустить раннюю модель.
Слова ограничены 5–16 символами, до 2 500 на язык и четырёх на семейство.
Это не исчерпывающий словарь и не независимые человеческие намерения.

| Раздел | Наблюдения префиксов, включая оба профиля | Семейства |
| --- | ---: | ---: |
| Train | 445 812 | 1 379 |
| Development | 62 598 | 203 |
| Calibration | 62 498 | 199 |
| Test | 55 322 | 181 |

Разбиение третьего поколения задано пространством имён
`keyswitch:prefix-v1:20260925:candidate3`, которое раньше не использовалось.
Первые два поколения делили те же слова иначе, и их test раскрыты, поэтому
семейства нового test пересекаются с train, development, calibration и test
прежних поколений. Этот кандидат на них не обучался, но и независимыми от
прежних экспериментов они не являются. Старые эксперименты завершённых слов
тоже могли видеть слова этого публичного снимка: это **не** глобально
неизвестный источник и не новые реальные диалоги. Шаблоны окружения
повторяются между частями; соседние слова не объявляются независимыми. Метка
ожидания для ошибочной раскладки с возможным исходным продолжением опирается
на индекс префиксов без Hunspell, но не на порог или решение прежнего
early-switch алгоритма.

Признаки: возможность/частота продолжений в обоих языках, известность,
n-граммы, длина и форма префикса, язык последних 512 символов, последние слова,
признаки комментария/присваивания/кавычек, приложение и роль поля. Словари —
те же, что использует движок: оценки слов (известность, n-граммы) — онбордовые
EN/RU-словари вместе с пакетным словарным дополнением
(`resources/lexicon-supplement-ru_RU.json`), индекс продолжений префиксов —
онбордовые словари и, где есть Hunspell, основы его словаря; дополнения в
индексе движка нет, нет его и здесь. Признаки frozen отдельно для профиля без
Hunspell (portable) и с эталонным Hunspell. Оба профиля — два измерения одних
ситуаций, а не независимые наборы пользовательских вводов. Для каждой строки
development и calibration признаки и решение прежнего алгоритма повторены
объектами, которые строит движок, — совпадение полное. Из конфигурации
intent-v1 корпус читает только пути и контрольные суммы словарей; веса
intent-v1 в корпус не входят.

## Обучение и зафиксированный результат

Детерминированный AdaGrad, до 35 эпох; эпоха выбрана по development loss
(лучшей оказалась последняя, 35-я), порог — только по calibration: первый из
заданного списка без ложных вмешательств на 4 239 ситуациях calibration в
каждом профиле, 0.985. Train определяет словарь признаков и веса классов. До
test сохранены config, кандидат и seal.

[Отчёт test](report.json): 3 740 ситуаций, 1 756 с неверной раскладкой,
каждая проверена в двух словарных профилях. Считается первое вмешательство
за последовательность, а не число уверенных прогнозов на отдельных буквах.

| Метрика | Portable | Reference Hunspell |
| --- | ---: | ---: |
| Нужная замена до конца слова | 1 722 / 1 756 (98.06%) | 1 739 / 1 756 (99.03%) |
| Нужная замена до границы включительно | 1 731 / 1 756 | 1 745 / 1 756 |
| Ложное вмешательство | 0 / 3 740 | 0 / 3 740 |
| Ложное вмешательство в командах/идентификаторах | 0 | 0 |
| Ложное вмешательство изолированного legacy-prefix | 222 | 246 |

В среднем замена происходит после 4.03 символа (portable) и 4.02 (Hunspell).
В test нет ложных вмешательств; сохранённые в отчёте примеры — неверная
раскладка, которую модель оставила до границы слова. На development при том же
пороге было по пять ложных вмешательств в каждом профиле (5 из 4 240, 0.12%) —
английские опечатки с удалённой буквой `enjy`, `enjys`, `enjyed`, `abue`,
которые модель переводит в русскую раскладку. Порог выбирается не по
development, исключения для этих слов не добавлялись; класс «опечатка или
чужая раскладка» остаётся слабым местом модели. Сравнение legacy-prefix не
равно сравнению с полным прежним `assist`: там ранняя замена была выключена.

Заранее заданные условия пройдены в каждом профиле: минимум 1 000 ситуаций,
ложные вмешательства ≤0.1% всех ситуаций, ноль технических ложных замен,
раннее исправление ≥70% нужных случаев, ложных вмешательств не больше legacy.
Это не сертификат отсутствия ошибок или проверка всех приложений.

## Движок и ограничения

[Сквозной отчёт](engine-report.json): 288 заранее выбранных test-ситуаций,
по 32 на категорию; два словаря × наблюдаемый/симулированный контекст поля.
Физические клавиши фиксированы, отображаемые символы следуют новой раскладке;
проверяется конечный текст вместе с двумя пробелами. Словари и индекс
префиксов — те же, что строит движок.

В каждом режиме восстановлены 127/128 ошибочных вводов против 126/128 у
варианта `assist` без ранней модели. До окончания слова — 113/128 и 114/128 с
наблюдаемым контекстом (portable, Hunspell) и 112/128 с симулированным чтением
поля. Потерь/добавлений символов по длине нет. Из 160 изначально корректных
примеров 19 остаются изменёнными — столько же, сколько у варианта без ранней
модели: в записанных примерах это команды после приглашения `$`, которые меняет решение по
завершённому слову. Ранний путь их не увеличил, но и не исправил. Это видимый
редактор внутри процесса, не реальный Windows hook или произвольный чат.

Отчёт закрепляет весь runtime: модули программы, установленные модели (в том
числе context-v1 и intent-v1), словарное дополнение и эталонные словари.
Первый отчёт этого кандидата снят до установки весов; после установки он
обновлён `--refresh-runtime` на тех же ситуациях с теми же числами, прежний
[сохранён](engine-history/a6254fc9a873a7fca555b9a3a4cc7f7fdb248b36ed45824ad3516ea6e779c0c5.json).
Обновление отчёта на тех же ситуациях не создаёт новой независимой оценки.

Движок ждёт отпускания всех клавиш, повторяет прогноз на актуальном префиксе,
сохраняет идентификатор поля при rollover и проверяет его перед инъекцией.
Фокус, безопасный диапазон замены, явная ручная раскладка, исключения и запреты
после Undo выше модели. ALL-CAPS/camelCase и неподдержанный диапазон не
обрабатываются ранней моделью. Недоступные/повреждённые веса запрещают именно
модельную раннюю замену, не ручной Pause и не проверку завершённого слова.

Модель не видит будущие символы, не является парсером языка программирования
или универсальным распознавателем паролей. Код без предшествующего синтаксиса,
редкие имена, иной словарь, нетипичный редактор и изменённый контекст могут
вести себя иначе. Ошибки допустимо оставлять без вмешательства. Ручной выбор
не заменяется вероятностным решением. Чтение настоящего поля остаётся opt-in;
соседний текст не добавляется в диагностику `prefix_decision`.

Нативные E2E и замер задержки выполнялись для первого поколения (ниже) и для
следующих не повторялись; схема признаков и extractor те же.

## Проверка без изменения кандидата

```sh
PYTHONPATH=src python3 tools/prefix_corpus.py
PYTHONPATH=src python3 tools/train_prefix_model.py verify
PYTHONPATH=src python3 tools/evaluate_prefix_engine.py --verify
PYTHONPATH=src python3 tools/verify_prefix_model.py
```

Запускать тяжёлые проверки последовательно. Обучение работает с замороженными
числовыми признаками и C-оптимизатором; engine replay требует reference
словарей. `verify` побайтно повторяет веса, seal и отчёт без продвижения.
Квитанция корпуса закрепляет байты кода, из которого посчитаны строки, и
источника, лексический контракт intent-v1 (пути и контрольные суммы словарей,
а не весь файл конфигурации), словарное дополнение и слова, которые оно даёт
каждому языку, а также значения, которые этот код берёт из
`keyswitch.constants` (`constants_sha256`); seal так же закрепляет тренер и его
значения. Поэтому новое поколение intent-v1 с теми же словарями проверку не
останавливает, а изменение словарей, дополнения, этих модулей или их значений —
останавливает до нового обучения prefix-v1.
Пакеты проверяют hash активного артефакта, corpus/seal/test и точный engine
отчёт. После раскрытия test команда `fit` запрещена; новый эксперимент требует
отдельной контрольной выборки. Engine-only `--refresh-runtime` архивирует
предыдущий отчёт и не выдаёт повторный тест за независимую оценку; установленный
артефакт входит в runtime отчёта, поэтому после установки весов отчёт
обновляется так же, а `train_prefix_model.py promote` перепроверяет всё и
записывает те же байты.
